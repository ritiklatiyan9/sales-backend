# Booking API

## Client registration, staff profile and named draws

Run `npm run migrate:client-flow` before starting this version. The repeatable migrations 029–033 add private staff and client credential tables, explicit KYC identity links, lookup indexes, a normalized mobile duplicate guard, and named-draw enrollment protection. Existing members, KYC, draw history and financial entries are retained. Sub-admins and agents use assigned sites; Admin and Super Admin retain access to all sites.

The Booking sidebar has **Clients** (`/clients`) for every authenticated site user. Register a name and Indian mobile number; optionally add PAN, Aadhaar, supporting Aadhaar front/back and PAN files, and an agent referral code. Uploaded identity files can fill blank fields through OCR before registration; users review the extracted details before saving. A client photo can be captured with the camera or uploaded. Registration creates or reuses the shared Accounting CLIENT and an accessible KYC case. Reusing a phone preserves the existing name and referring agent, fills missing identifiers/contact details, and rejects conflicting PAN/Aadhaar or referral claims. Registered details prefill KYC; documents and photos use the existing KYC storage and are not automatically marked verified.

**New Booking** (`/bookings/new`) starts with registered-client mobile lookup. Select the person and enter a draw name/code such as A1 or B5, then continue into the existing payment, KYC, slip, physical result and allotment workflow. A client can have separate entries in multiple named draws. Retries reuse the request; a second active entry for the same normalized draw name returns `409 DRAW_ALREADY_ENROLLED`. Cancelling an entry permits a new enrollment. Staff can switch to Direct booking.

**My Profile** (`/profile`) updates name, email, mobile and password. Super Admin, Admin and Sub-Admin can sign in with registered email/password or phone/password. Staff may enroll Aadhaar as an initial phone password from Profile using their current password. The existing users table has no trusted Aadhaar field/link, so existing staff must enroll it once rather than borrowing a client’s KYC identity. Aadhaar is hashed in `booking_staff_identities`, never returned as plain text. A new custom password replaces the initial Aadhaar password and works with both email and phone. Sensitive profile changes revoke old access/refresh tokens and OTP challenges while issuing replacement tokens to the current browser. An Accounting password change also disables an older Aadhaar credential.

New/extended APIs:

- `POST /auth/login`: `{identifier,password}`; legacy `{email,password}` remains accepted.
- `PATCH /auth/profile`: own `{name,email,phone,current_password,new_password,aadhaar_number}`; send only fields being changed. Role/permission changes are rejected.
- `GET /clients?site_id=&q=&page=&limit=`: paginated directory with masked PAN/Aadhaar and grouped draw counts. Search uses indexed name/mobile prefixes.
- `POST /clients`: `{site_id,full_name,phone,pan_no?,aadhar_no?,agent_referral_code?,father_name?,date_of_birth?,gender?,address?,city?,state?,pincode?,registration:true}`.
- `POST /clients/identity/preview`: multipart `file`, `site_id`, and `type` (`AADHAAR` or `PAN`). Site-authorized OCR preview, limited to 10 MB PDF/JPG/PNG/WebP, with normalized `member_fields` and a short-lived `preview_key`. No client or KYC record is created by a preview.
- `POST /clients/:id/documents`: multipart `file`, `type` (`AADHAAR`, `PAN`, `PHOTO`, `OTHER`), optional `member_document_field`, and optional `preview_key`; `GET` lists accessible documents with view URLs. A preview is reused only for the same actor, site, type and file bytes within 10 minutes. Photos allow JPG/PNG/WebP up to 5 MB and also update the shared client photo.
- `POST /draws`: existing contract with registered `client_member_id`, `scheme_name`, and a stable `request_key`.

Validation: `npm run test:client-flow` in both Booking repositories; `npm run test:booking-workflow` in this backend; `npm run build:booking` in the frontend. Database tests run on isolated PostgreSQL and do not create live clients, staff credentials, payments or draw entries.

Existing accounts with no stored Clients permission retain access. Shared client search/detail lookups stay available to permitted booking, draw and KYC flows.

Re-running the migration preserves the saved order. This setting has no site/user filter and does not change module permissions or site assignments.

Admins choose **Arrange**, drag the grip (or use Space/arrow keys or move buttons), then **Save for all users**. New modules are reconciled into existing layouts. Validate with `npm run test:sidebar` in both Booking repositories.

Application Form Studio and issued forms use four A4 faces in sequence: applicant, terms, commercial, and slip/token. Print all four pages, one page per side, double-sided with **long-edge flip**, **100% / actual size**, and browser headers/footers disabled. Pages 1/2 share sheet 1; pages 3/4 share sheet 2. ## Private client dashboard and KYC identity links

**Client login is currently disabled.** `CLIENT_PORTAL_ENABLED` defaults to false and is set to false in the local environment. Client phone sign-in, refresh, and every client portal API return no client access, including requests with previously issued client tokens. Staff and linked broker login remain available. The Clients staff page uses a directory-first phone layout with Clients/Register tabs, document reading, camera/upload controls and a sticky save action.

The retained client portal is available only if explicitly enabled with `CLIENT_PORTAL_ENABLED=true`. In that mode, verified CLIENT members can sign in at `/login` using their KYC mobile and Aadhaar. First successful sign-in creates a private `booking_client_accounts` entry and links only verified CLIENT records with the same normalized mobile and exact Aadhaar. It never creates or modifies a shared staff `users` account. Clients land at `/client-portal`, which has their own bookings, draw entries, payments, masked KYC details, documents and password change.

Client JWTs use a distinct issuer, audience and purpose-specific keys derived from `CLIENT_PORTAL_SECRET`. Accounting and Booking staff APIs reject these tokens. Client refresh is at `/client-portal/auth/refresh`; ownership is resolved from private account/member links on every request. Record IDs or client-supplied site/member filters cannot grant access. Payment visibility uses owned booking token references and owned draw payments; historical plot ownership never exposes another buyer’s ledger. Documents stream through an authenticated ownership check. Password changes and logout revoke client sessions; the old Aadhaar cannot restore a chosen custom password.

Set independent random `CLIENT_PORTAL_SECRET` and `CLIENT_PORTAL_IDENTITY_SECRET` values in the backend environment. Keep the identity key stable when rotating signing keys; it protects identity matching without storing raw Aadhaar in the account table. Never expose these through frontend variables.

Staff phone login remains limited to Super Admin, Admin, Sub-Admin and `agent` users explicitly linked to a verified BROKER member. An operator/referrer is never assumed to be the KYC subject. **Link staff login** on a KYC page requires an authorized Admin/Super Admin, explicit account selection and the actor’s current password. Initial Sub-Admin and broker links require this confirmation. Linked profiles display imported mobile, source KYC and masked Aadhaar. Ordinary OCR/KYC edits cannot silently reset account credentials.

`npm run migrate:client-flow` includes all required migrations. Run `npm run test:client-portal` and `npm run test:kyc-login` for isolated ownership, credential and token-isolation checks. No test signs into a real customer’s account or creates live financial rows.

## Payment and approval lifecycle

`POST /public/website/orders` accepts `{plot_number,buyer_name,buyer_phone,buyer_email,buyer_address,terms_accepted:true,idempotency_key}`. It ignores client-supplied amounts and project ids. The server locks settings and the selected Company plot, checks existing bookings, reserves it once and creates an INR Razorpay order. A retry with the same random key reuses its saved order; changed details are rejected. Native booking creation and draw allotments use the same plot lock and cannot bypass a website hold.

The website's framework-equivalent endpoints are `POST /api/booking/orders` and `POST /api/booking/payments/verify`. Order responses retain the existing format `{request_token,key_id,order:{id,amount,currency},...}`; **`order.amount` is in paise**, whereas the request's display `amount` is in rupees. The Node Razorpay SDK makes the authenticated server request to `POST https://api.razorpay.com/v1/orders`. Orders below 100 paise return 400; provider authentication failures return 401; other provider failures return 500 with safe messages. Timeout/uncertain responses preserve the reservation for reconciliation.

Checkout callbacks call `POST /public/website/payments/verify` with `{request_token,razorpay_order_id,razorpay_payment_id,razorpay_signature}`. The HMAC uses the saved server order id. The server also fetches payment and order, requiring the exact INR amount, captured payment and no refund. Payment moves the request into `PAYMENT_REVIEW`; it does not automatically allot the plot.

Missing callback fields and signature mismatches return 400 without marking the request paid. The frontend loads `https://checkout.razorpay.com/v1/checkout.js`, shows cancellation/payment failure messages, and waits for server verification before reporting payment received. A dismiss callback after successful checkout cannot interrupt that verification. The public key ID is returned from backend environment configuration, so no frontend key variable is needed; the secret never enters the website bundle.

An opaque request token permits only its own sanitized recovery at `GET /public/website/requests/:token` and `POST /public/website/requests/:token/reconcile`. Recovery fetches the saved order's payments when a browser callback was lost. Valid unpaid requests expose the saved order/key for Checkout resumption. Access logs redact these recovery tokens. Never put them into analytics events or external URLs.

Staff uses `POST /website-management/requests/:id/reconcile`, `/approve` or `/reject`. Approval rechecks the gateway and the locked refund state, mapping, plot availability and duplicate bookings. One transaction creates/reuses the verified customer's CLIENT record, creates a KYC booking with a case, updates the plot to BOOKED and writes exactly one shared `plot_payments` BANK/RAZORPAY entry. That entry remains `pending` for the Accounting application's existing approval workflow; website approval does not invent a financial receipt or bypass Accounting permissions.

Captured website payment/plot fields are immutable in booking edits. Cancelling a booking preserves its captured ledger entry and flags refund assistance; its public status becomes `CANCELLED`. Its audit record cannot be deleted. Rejecting a paid request also flags `refund_required`. No refund is issued automatically. Complete refunds in Razorpay and use the Accounting workflow for any approved ledger/booking correction.

Expired or late captures can become `PAYMENT_CONFLICT` if another request holds the plot or availability changed. Staff must resolve the payment/refund; such requests cannot take the other customer's reservation. A gateway creation timeout preserves `ORDER_CREATING` and never creates a second order on retry. Staff can recover it with the merchant dashboard's order id; the server verifies the saved receipt and amount before linking it. The queue displays the receipt for that purpose.

## Webhooks and deployment

Configure the HTTPS backend route `/public/website/webhook` in the Razorpay dashboard for `payment.captured`, `order.paid`, `payment.refunded` and `refund.processed`, with a secret matching backend `RAZORPAY_WEBHOOK_SECRET`. This route verifies HMAC over the original bytes before JSON parsing. Gateway verification and event id deduplication make retries safe. Refund events must match the request's linked payment, amount and currency. A local localhost route is not reachable from Razorpay; opaque token recovery and staff reconciliation remain available during local testing.

Enable automatic capture in the Razorpay dashboard. Test keys simulate payments; use separate live credentials only after test checkout, callback recovery and staff approval have been exercised. Keep the webhook secret independent of the API secret.

The website proxy applies per-visitor limits. Backend public routes have a coarser bounded process-local limit because proxy connections can share an IP. For direct external API access, enforce visitor limits at the deployment ingress; configure `TRUST_PROXY` only for known proxy subnets (for example `loopback` locally), and preserve the actual visitor IP at that trusted ingress. The database plot locks, unique active reservation index and idempotency keys remain authoritative across workers; process-local rate limits are not a substitute for ingress limiting.

Official Razorpay integration guidance: [Checkout signatures and captured status](https://razorpay.com/docs/server-integration/python/test-app/), [security checklist](https://razorpay.com/security/checklist/).

## WhatsApp notifications (AWS End User Messaging Social)

Run `npm run migrate:whatsapp`, `npm run migrate:whatsapp-studio`, `npm run migrate:whatsapp-marketing`, and `npm run migrate:whatsapp-template-management` before starting this API version. Migration 039 adds `whatsapp_messages` (outbox and delivery log); migration 040 adds `whatsapp_templates` (every template version sent to Meta) and `whatsapp_stage_settings` (per stage on/off and attachment). Migration 042 adds template titles, archive dates, and explicit stage assignments. It pins each stage's newest currently approved version once to preserve live behavior; rerunning preserves later choices, including an explicit unapply. The migration makes no AWS calls. Customers (`member_type = CLIENT`) get the applied approved template per stage on `members.whatsapp`, else `members.phone`, as a `+91` mobile:

- **Client registered**: a new client from `POST /clients`, `POST /kyc/cases` (mobile quick-add) or `POST /kyc/fresh-form/commit`. Reused or existing members, brokers and staff get nothing.
- **KYC verified**: `POST /kyc/case/:id/verify`, onboarding auto-verify, and the Accountancy verify (`/member-kyc/case/:id/verify` in rgaccountbackend, where most verifications happen; it queues the same row when its own `WHATSAPP_ENABLED=true`).
- **Draw payment received**: `POST /draws/:id/payments` (new receipts only; request-key retries never resend). Attaches the payment receipt PDF, rendered on the server with the printed receipt's sections (`src/services/whatsappDocuments.js`).
- **Booking made**: `POST /bookings` and website request approval. The message names the unit.
- **Plot / shop allotted**: draw allotment (draw winners get only this one), or a unit assigned or changed later through `PUT /bookings/:id`.

**WhatsApp Studio** (`/whatsapp-studio`, admin and super_admin) groups the five real notification triggers into Clients, Bookings and Lucky draw modules and submodules. Each stage exposes its applied template, full version library, available fields, attachment options and delivery activity. Only its explicitly applied, approved, non-archived version sends. Submitting or approving a new version never changes that choice; applying `template_name: null` leaves it unassigned without falling back to an older version. A document template requires a compatible attachment before it can be applied.

Templates have a local title (up to 80 characters) and can be archived and restored without deleting their approval at Meta. Applied templates must be unapplied before archive or delete, even when the stage is paused. A transactional message already sending for that stage must finish first. Restore does not reapply a template. Deleting removes the remote Meta template and hides it from the library while retaining its name and delivery history. A running marketing campaign also protects its template from deletion. API:

- `GET /whatsapp/studio`: stages include `module`, `submodule`, `trigger`, `settings.template_name`, `active_template` (object or null), and `templates` with `title`/`archived_at`.
- `PUT /whatsapp/stages/:event`: partial `{enabled, attachment, template_name}`; omitted settings stay unchanged, and null `template_name` explicitly unapplies. Only approved, non-archived templates created for that event can be applied.
- `POST /whatsapp/templates`: `{event, title, body, has_document}` creates a version for Meta review without applying it.
- `PATCH /whatsapp/templates/:name`: `{title?, archived?: boolean}` renames, archives or restores transactional templates locally.
- `DELETE /whatsapp/templates/:name`, `POST /whatsapp/test` `{event, phone}`, `GET /whatsapp/documents/:key/sample` retain their existing roles. Tests use the applied approved version and sample values.

Hooks only insert a QUEUED row after their transaction commits; the API worker sends queued rows every 10 seconds, one claim at a time, and refreshes Meta approvals every 10 minutes, so WhatsApp never fails or delays a request. `dedupe_key` sends each event once (for unit changes, once per from→to move); rows older than a day expire unsent. Stages turned off, stages without an approved template, cancelled bookings, non-clients and invalid numbers are recorded `SKIPPED` with the reason; AWS errors `FAILED`. A send cut off by a restart turns `FAILED` after 10 minutes with a note to check the customer first, because it may have arrived. Resend after fixing with `UPDATE whatsapp_messages SET status = 'QUEUED', created_at = now() WHERE id = …`. Only plain names are printed; names with digits, links or more than 60 characters are sent as "Customer". The unit word is the site's **Booking settings → Documents → Property type** when set, otherwise "Shop" for draw allotments and "Plot" otherwise.

1. In the AWS console (region `ap-south-1`) open **AWS End User Messaging Social → Add WhatsApp phone number**, finish Meta's embedded signup with a number that is not on the WhatsApp or WhatsApp Business app, and copy the `phone-number-id-…` value. The AWS account must be on a paid plan; free-plan accounts get `SubscriptionRequiredException`.

## WhatsApp Marketing

Run `npm run migrate:whatsapp-marketing` (migration 041, additive): it adds `site_id`/`options` to `whatsapp_templates`, `campaign_id` to `whatsapp_messages`, and the `whatsapp_campaigns` and `whatsapp_opt_outs` tables. **WhatsApp Marketing** (`/whatsapp-marketing`, admin and super_admin) works on the site selected in the sidebar: build a MARKETING template (text with `{customer_name}`/`{project}`, optional JPG/PNG header image up to 5 MB, optional website and call buttons) with a live preview, submit it to Meta, send a test, then send it to every active CLIENT of the site with a valid mobile (one message per number; numbers on the do-not-message list are left out). The page shows reach, an estimated cost (about ₹1.35 per delivered message to India, Meta + AWS, GST extra) and how many days the daily limit needs. **Choose customers** (`/whatsapp-marketing/customers`) lists every active client of the site in a table (mobile, KYC, bookings, draws, whether WhatsApp can reach them) with search and filters; tick customers (only reachable ones can be ticked) and send an approved template to just them.

Marketing Studio uses the same shadcn template-library and dialog workflow as transactional WhatsApp Studio. Its tabs separate templates, campaign creation, campaign activity, and the do-not-message list. Each template shows its project and recent campaign use. Approved, unarchived templates can be selected for a campaign; selecting one never queues messages. Both all-customer and selected-customer sends require a review dialog. Edited versions retain the original image and action buttons unless removed.

Migration 042 (already required by WhatsApp Studio) supplies marketing template `title` and `archived_at`; this update adds no migration. `PATCH /whatsapp/marketing/templates/:name` accepts `site_id` plus `title` and/or `archived`; `DELETE /whatsapp/marketing/templates/:name?site_id=` permanently removes an unused template. Both verify the template belongs to the requested accessible project. Archive/restore retains Meta approval. Archive/delete is blocked while campaign messages are queued or sending, including cancellation with an in-flight message. Campaign creation locks the template so archiving cannot race with queueing. `POST /whatsapp/marketing/templates` additionally accepts `source_template` and `reuse_image=true` when copying an existing image in the same project.

Both template editors and the API reject more than two consecutive newline characters and more than 10 emoji graphemes before submission. Editors show character/emoji counts and an explicit Clean spacing action. These checks cover the provider rejection observed in the editor; Meta can still reject content for other reasons.

A campaign queues one `whatsapp_messages` row per customer. The worker sends booking/KYC messages first and campaign messages only while `WHATSAPP_MARKETING_DAILY_LIMIT` (default 200 per rolling 24 hours) allows, so a large campaign spreads over days; campaign rows do not expire. Cancelling skips whatever has not gone. Header images are stored under `marketing/` in `WHATSAPP_MEDIA_BUCKET` (kept; `whatsapp/` PDFs expire after 30 days) and uploaded to WhatsApp once per campaign. The do-not-message list (`whatsapp_opt_outs`) applies to every site and to marketing only; booking and KYC updates still reach those customers. Campaigns refuse to start while `WHATSAPP_ENABLED` is not `true`, and a template cannot be deleted while a campaign still sends it. API: `GET /whatsapp/marketing?site_id=`, `POST /whatsapp/marketing/templates` (multipart: site_id, title, body, image, website_text/url, call_text/phone), `GET /whatsapp/marketing/customers?site_id=`, `POST /whatsapp/marketing/test`, `POST /whatsapp/marketing/campaigns` (optional `member_ids` sends only to those customers; ids that cannot be reached are dropped), `POST /whatsapp/marketing/campaigns/:id/cancel`, `POST`/`DELETE /whatsapp/marketing/opt-outs`.

Message only customers who agreed to receive offers. Offers share the number with booking and KYC updates: blocks and reports lower its quality rating for both. Validate with `npm run test:whatsapp`.

## Booking security hardening (20 October 2026)

The application cannot be made “attack proof,” and browser developer tools cannot be disabled by a website. The Booking frontend now suppresses the page context menu and handles common inspection shortcuts as a UI deterrent. Native browser shortcuts, browser menus, disabling JavaScript, extensions and direct HTTP clients can bypass it. Copy, paste, print and ordinary keyboard navigation remain available. Trusted developers can set `VITE_PREVENT_INSPECTION=false` in their build; no access-control decision depends on that flag. Production Booking builds explicitly omit source maps, but downloaded JavaScript is still readable.

Implemented protections:

- Password/Google/OTP sign-in, refresh, public verification and document uploads have bounded per-process request limits. Sign-in also limits a normalized account identifier per IP. Forwarding headers are only trusted through an explicitly configured `TRUST_PROXY`; limits return HTTP 429 with `Retry-After`. Multiple API replicas need a shared limiter or limits at the reverse proxy/WAF; restarting a process resets these counters.
- Realtime OCR notifications are no longer broadcast globally. Subscriptions and each delivery check the live account, session version, site, module and booking/KYC network ownership. Expired/revoked sessions lose delivery access. Subscription counts, join attempts and socket payload size are capped.
- JWT verification explicitly accepts HS256, matching Accounting, and staff sessions check current active status, token version, expiry and current role. OTP guesses reserve attempts atomically, and the correct challenge is consumed atomically before tokens are issued. Enabling OTP never silently bypasses it when SMTP is absent.
- Uploads require an exact supported extension, matching MIME and recognizable file signature; multipart field/file counts, field sizes and requests per user are limited before storing or OCR. File signatures are basic validation, not malware detection. JSON is limited to 2 MB; URL-encoded forms are limited to 256 KB/100 fields. Multipart documents retain the 10 MB file limit.
- Unexpected server errors no longer expose database/provider messages or stacks. Access logs omit query strings and redact public recovery tokens. Authenticated/auth/public verification responses use no-store caching. Production origins are explicit; socket and REST origin policies match. CORS is not authorization and does not stop direct HTTP clients.
- Database TLS verifies certificates by default (`DB_SSL_CA` supports a private CA). Production refuses weak/equal JWT secrets, wildcard CORS, globally trusted proxies, disabled certificate verification and explicitly enabled OTP without SMTP. Coordinate shared JWT secret rotation with Accounting; this patch does not rotate deployed secrets.
- Production refuses the local upload fallback and does not statically serve `/uploads`; configure S3 before deploying. Vercel config supplies nosniff, same-origin framing, referrer/permissions policy, HTTPS HSTS and a limited CSP for base URLs, objects, framing and form submissions. This is not a strict script CSP; a stricter policy needs testing against Firebase login, print windows and embedded Accounting.

Remaining work before treating the deployment as hardened:

1. KYC files are also linked onto Accounting member columns with durable public S3 URLs (`getPublicKycUrl`). Those existing shared URLs and S3 bucket ACLs remain unchanged. Migrate Accounting and Booking together to authorized document downloads/private storage; closing an API endpoint cannot make an already public S3 object private.
2. Staff refresh/access tokens remain in shared browser localStorage for Accounting compatibility. An HttpOnly Secure cookie/session migration and XSS defenses must cover both applications; right-click blocking offers no token protection.
3. The frontend registry audit before/after compatible patches reduced reported dependency entries from 20 to 18 (15 high, 3 moderate remain). Axios 1.20.0, Socket.IO client 4.8.4 and parser 4.2.7 were installed. Remaining reports include SheetJS, React Router, Firebase transitive packages and tooling; report counts do not establish browser exploitability. No force/major-version upgrades were applied. Backend external registry auditing was blocked by automatic review and then declined by the user; it has not been performed. No further external checks were requested after that preference.
4. Production deployment, HTTPS/proxy configuration, private bucket policies, working administrator MFA, shared rate limiting, backups/restore, dependency remediation and an independent penetration test remain deployment work. This change does not publish or change cloud access policies.

Run `npm run test:security` in both `sales-backend` and `sales-dg-frontend`. The API tests use isolated PostgreSQL data/signing keys for OTP concurrency and injected ownership checks for realtime authorization; they do not attack a live service. Also run the API `npm run test:client-flow` and frontend `npm run build:booking`. The local API `/health` returned HTTP 200 after the changes.

Reference: [OWASP authorization guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html), [OWASP frontend security guidance](https://cheatsheetseries.owasp.org/cheatsheets/Web_Frontend_Security_Cheat_Sheet.html) and [OWASP CSP guidance](https://cheatsheetseries.owasp.org/cheatsheets/Content_Security_Policy_Cheat_Sheet.html).


Sub-admin permissions: `/access` now lets admin/super-admin users edit a sub-admin's View/Create/Update/Delete flags and site assignments. Sub-admins retain their previous defaults when a module has no row, but explicit denials are enforced at the API as well as in navigation. A disabled View also denies all actions in that module. Shared client/KYC lookups remain available to other authorized workflows. Full admin/super-admin CRUD bypass and existing business role restrictions (for example website payment review and draw decisions) remain in place; a module grant does not promote a user's role. Sub-admins cannot change their own or peer sub-admin access, or reset a protected account through agent editing. Company and banking settings use separate Update grants. Run `npm run test:access-control` in the API and UI (set `REACT_TEST_RENDERER_MODULE` to a matching React test renderer for UI interaction checks).


## dgbooking.com OCR deployment recovery

A successful frontend build does not mean the Booking API deployed successfully. When Render logs `JWT_ACCESS_SECRET must be an independent random secret of at least 32 bytes`, `node src/server.js` exits before listening. The new API is not live; a previous deployment can keep serving the old Mistral/Groq OCR error. Keep the production security check enabled.

1. Generate **two different secrets**, each using `openssl rand -hex 32` (run twice). Configure `JWT_ACCESS_SECRET` and `JWT_REFRESH_SECRET` on the Booking API and set their matching counterparts on the shared Accounting API to the same values. Access and refresh secrets must differ from each other; each must match across the two backends. Coordinate both redeployments. Existing sessions will need to sign in again. Enter secrets directly into the hosting dashboards; never send them through chat, commit them, or put them in frontend `VITE_` variables.
2. On the **Booking API Render service**, configure `OPENROUTER_API_KEY` with a valid funded OpenRouter key. Current OCR uses OpenRouter only; the former `MISTRAL_API_KEY` and `GROQ_API_KEY` do not configure it. Optional model/timeouts and their current defaults are in `.env.example`.
3. Redeploy the current backend commit, and confirm Render reports the service live and `/health` returns HTTP 200. A health response alone does not verify OCR or prove a new revision replaced an older one; check the deployed commit in Render. Diagnose any additional startup configuration errors before retrying OCR.
4. Vercel's `VITE_API_BASE_URL` must point at the deployed Booking API (normally `https://sales-backend-ponq.onrender.com`), not localhost or the static dgbooking.com frontend. Rebuild the frontend after changing a Vite environment variable. Both dgbooking.com origins are allowed by the API's origin list.
5. Sign in again after secret rotation. Use `/clients` to preview a clearly marked fictional identity image before testing a real applicant. Preview reads a document without creating a client; do not press Save for a diagnostic record.

Expected OCR setup, credential, credit and model errors now return safe messages and stable codes to the form, including on 503 responses. Unexpected server errors still stay generic and never return raw provider responses or keys. Production credential changes and redeployment are operator actions; local code/tests cannot certify the live environment before those steps complete.
